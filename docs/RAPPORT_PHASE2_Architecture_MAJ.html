01Principes et alignement avec le projet IntelliJ

Ce rapport définit l'architecture technique du backend Spring Boot pour le projet Logement étudiant à Monastir. Il est strictement aligné sur l'environnement IntelliJ déjà créé par l'équipe de développement.

Informations du projet IntelliJ :
  • Nom du projet : LogEtd
  • Package racine : org.logetd
  • Dossier des sources : src/main/java/org/logetd/
  • Dossier des ressources : src/main/resources/
  • JDK : OpenJDK 17 ou 25

Contraintes structurantes

  • Framework : Spring Boot 3.5.x, Maven.
  • Base de données : PostgreSQL (création automatique des tables via ddl-auto=update).
  • Architecture : Monolithe modulaire (découpage strict par packages).
  • Public : Étudiants de Monastir.
  • Paiement : Hors plateforme (D17, virement, espèces) avec double confirmation.
  • Outils : 100 % gratuits.

02Architecture globale

Monolithe modulaire

Pour un développeur unique assisté d'agents IA, les microservices ajoutent une complexité inutile. Le choix est un monolithe modulaire : un seul déploiable, mais des frontières de packages strictes pour éviter le code spaghetti. 

LogEtd/
├── src/main/java/org/logetd/
│   ├── LogEtdApplication.java
│   ├── config/       (Sécurité, Configuration CORS, Beans)
│   ├── shared/       (Énumérations, Exceptions, Utils)
│   ├── domain/
│   │   ├── user/     (User)
│   │   ├── listing/  (Listing, Place, Photo)
│   │   ├── booking/  (Booking, Visit)
│   │   ├── payment/  (Payment)
│   │   ├── messaging/(Message)
│   │   └── admin/    (Report, AuditLog)
│   ├── repository/   (Interfaces Spring Data JPA)
│   ├── service/      (Logique métier)
│   ├── controller/   (Endpoints REST)
│   └── dto/          (Data Transfer Objects - Request/Response)
├── src/main/resources/
│   ├── application.properties
│   └── db/migration/ (Scripts Flyway pour contraintes SQL pures)
└── pom.xml
Règle de dépendance : Un contrôleur ne parle qu'à un service. Un service ne parle qu'à des repositories. Aucune entité JPA ne sort du service sans être convertie en DTO.

03Structure des packages et du code

Le code doit être organisé de manière à séparer clairement les responsabilités.

PackageContenu

org.logetd.domain.*Les entités JPA avec annotations @Entity et @Table.
org.logetd.repositoryInterfaces héritant de JpaRepository.

05Conception de l'API et contrat

REST, versionné, documenté par OpenAPI

  • Préfixe d'URL : /api/v1/...
  • Pagination obligatoire sur les listes (paramètres page et size).
  • Erreurs standardisées : le serveur renvoie toujours un JSON avec code, message, details, timestamp.

Documentation de l'API

Le backend doit exposer un contrat clair. Tous les endpoints (Auth, Listings, Bookings, Payments) doivent être documentés au fur et à mesure dans le fichier docs/05-api/API_ENDPOINTS.md afin que les agents web (React) et mobile (Kotlin) puissent s'y connecter sans ambiguïté.

06Sécurité et authentification

  • Authentification : JWT (access token court + refresh token).
  • Bibliothèque : Spring Security.
  • Mots de passe : BCrypt avec un coût de 12.
  • Rôles : ROLE_TENANT, ROLE_OWNER, ROLE_ADMIN.
  • Validation : Utilisation stricte de Bean Validation (@NotNull, @Size, etc.) sur tous les DTOs d'entrée.
Point de vigilance : Le rôle ROLE_ADMIN ne doit jamais être accessible via un formulaire d'inscription public. Il est créé manuellement ou via un script d'initialisation.

07Contrainte anti-chevauchement (Point critique)

C'est le cœur de la fiabilité de la plateforme. Il doit être impossible pour deux étudiants de réserver la même place aux mêmes dates.

Pourquoi Hibernate ne suffit pas : Même avec un if en Java, si deux requêtes arrivent exactement au même moment, les deux pourraient passer. La seule solution fiable est de déléguer cette sécurité à PostgreSQL.

Implémentation SQL (via Flyway)

Bien que nous utilisions ddl-auto=update pour le reste, cette contrainte spécifique doit être ajoutée via un script SQL pur dans src/main/resources/db/migration/V1__exclusion_constraint.sql : 

CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings
ADD CONSTRAINT no_overlap_active_booking
EXCLUDE USING gist (
    place_id WITH =,
    daterange(start_date, end_date, '[]') WITH &&
)
WHERE (status IN ('ACCEPTED', 'DEPOSIT_PENDING', 'CONFIRMED', 'IN_PROGRESS'));

Si le code Java tente d'insérer un chevauchement, PostgreSQL lèvera une exception. Le code Java doit attraper cette exception et renvoyer une erreur HTTP 409 Conflict avec le code métier BOOKING_DATES_UNAVAILABLE.

08Stratégie multi-agents et coordination

Le projet est développé par plusieurs agents IA coordonnés par un humain. Le dossier docs/ est la mémoire unique du projet.

DossierRôle
00-contextVision, contraintes (PROJECT.md)
01-specsRapports fonctionnels et d'architecture
02-architectureContrat API global (API_CONTRACT.md)
03-tasksSuivi des tâches étape par étape (TASKS.md)
04-conventionsRègles de code (CONVENTIONS.md)
05-apiListe des endpoints (API_ENDPOINTS.md)
06-decisionsJournal des choix techniques (DECISIONS.md)
Règle d'or de validation : L'agent réalise UNE étape (ex: Étape 1 - Initialisation), s'arrête, et demande validation à l'humain. L'humain teste (app démarre, tables créées dans pgAdmin), puis autorise le passage à l'étape suivante (Étape 2 - Auth).

09Feuille de route de développement

ÉtapeContenuLivrable démontrable
1 · Initialisation Projet Spring Boot, packages, entités JPA, configuration PostgreSQL. L'application démarre, les tables sont créées.
2 · Authentification Register, Login, JWT, Rôles. Un utilisateur peut s'inscrire et se connecter.
3 · Annonces CRUD Listings et Places. Un propriétaire crée une annonce.
4 · Recherche Filtres, pagination. Recherche avec critères (prix, meublé, etc.).
5 · Réservations Visites, Bookings, contrainte anti-chevauchement. Un étudiant réserve, la base bloque les doublons.

10Risques et décisions retenues

Décisions validées

  • Architecture : Monolithe modulaire (pas de microservices).
  • Base de données : PostgreSQL avec ddl-auto=update pour la simplicité, et Flyway pour la contrainte SQL pure.
  • API : REST versionné, documentation OpenAPI.
  • Sécurité : JWT + BCrypt coût 12.
  • Coordination : Travail par étapes avec validation humaine obligatoire.

Risques surveillés

  • Concurrence de réservations : Géré par la contrainte PostgreSQL (test critique obligatoire).
  • Fuite de données : Masquage des adresses exactes avant visite, téléphones masqués avant réservation.
  • Dérive des agents IA : Neutralisé par le dossier docs/ (règles strictes) et l'arrêt obligatoire à chaque étape.
