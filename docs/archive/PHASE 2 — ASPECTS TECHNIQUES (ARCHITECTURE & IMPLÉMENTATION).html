01Principes directeurs et périmètre

Ce rapport traduit en choix techniques les spécifications fonctionnelles de la Phase 1. Il ne redéfinit pas le produit : il indique comment le construire avec un développeur unique, un budget nul et une fenêtre de trois semaines, tout en produisant un livrable crédible devant un jury.

Règle d'or : à tout moment, il existe une version qui fonctionne. On avance par niveaux de priorité (noyau → étudiants/travailleurs → si le temps le permet → perspectives). Ce qui n'est pas terminé devient une perspective documentée, jamais un trou dans la démo.

Contraintes structurantes

  • Backend imposé : Spring Boot (Java).
  • Frontend web : React (+ choix recommandés).
  • Mobile : Android d'abord, exigé par le jury.
  • Outils exclusivement gratuits (open source ou licence éducative).
  • Paiement hors plateforme (D17, virement, espèces) avec double confirmation.
  • Trois villes, trois segments, un seul administrateur au départ.

02Architecture globale

Monolithe modulaire, pas de microservices

Pour un développeur unique, trois semaines et une seule instance, les microservices ajoutent du coût (réseau, orchestration, débogage distribué) sans bénéfice. Le choix est un monolithe modulaire : un seul déployable, mais des frontières de modules explicites, vérifiées automatiquement par Spring Modulith. Le build échoue si un module viole la frontière d'un autre. C'est aussi une excellente illustration d'architecture pour le jury. 

backend/src/main/java/tn/rental/
  ├── auth/          (comptes, rôles, JWT)
  ├── listings/      (annonces, photos, règles, validation)
  ├── search/        (recherche, filtres, pagination)
  ├── bookings/      (demandes, statuts, anti-chevauchement)
  ├── payments/      (D17, virement, espèces, double confirmation)
  ├── messaging/     (messagerie, WebSocket)
  ├── reviews/       (avis croisés)
  ├── notifications/ (push, e-mail, in-app)
  ├── admin/         (back-office, signalements, litiges)
  └── shared/        (erreurs, sécurité, configuration, audit)
Règle de dépendance : un module n'utilise que l'interface publique d'un autre module. Aucun accès direct aux entités JPA d'un autre module. Les échanges passent par des DTO ou des événements internes.

Pas de BFF, pas d'API Gateway. Avec un seul backend et deux clients, une gateway serait une couche vide. Elle est mentionnée comme perspective si le nombre de clients ou de services augmentait.

Contrainte anti-chevauchement

Le cœur de la confiance sur les dates. Implémentée en SQL pur dans une migration Flyway, sous forme de contrainte d'exclusion PostgreSQL sur les réservations actives d'un même bien. 

-- Migration Flyway (exemple simplifié)
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE booking
  ADD CONSTRAINT no_overlap_active_booking
  EXCLUDE USING gist (
    listing_id WITH =,
    daterange(start_date, end_date, '[]') WITH &&
  )
  WHERE (status IN ('ACCEPTED','PAYMENT_PENDING','CONFIRMED'));
Point critique. La base lève une violation de contrainte en cas de concurrence. Le code doit l'attraper et renvoyer 409 BOOKING_DATES_UNAVAILABLE, jamais une exception non gérée. Ce comportement doit être couvert par un test avec deux demandes simultanées.

Stratégie de migration

  • Flyway seul modifie le schéma. JPA est en ddl-auto=validate : toute divergence fait échouer le démarrage.
  • Une migration = un fichier versionné (V1__init.sql, V2__booking_exclusion.sql…), jamais modifié après application.
  • Les données de démonstration passent par un script séparé (R__demo_data.sql), pas par les migrations de schéma.
Temps et montants. Dates de séjour stockées en date simple (sans heure). Horodatages en UTC, convertis en Africa/Tunis à l'affichage. Montants en millimes (entiers), jamais en flottants.

04Conception de l'API

REST, versionné, documenté par OpenAPI

  • REST plutôt que GraphQL : plus simple, mieux outillé, adapté à deux clients.
  • Versionnement par préfixe d'URL : /api/v1/....
  • Pagination obligatoire sur les listes, taille maximale limitée.
  • Erreurs standardisées : code métier stable + message + détails de validation.
  • OpenAPI généré par springdoc-openapi, servant de contrat pour le web et Android.

Format d'erreur standard

{
  "code": "BOOKING_DATES_UNAVAILABLE",
  "message": "Ces dates ne sont plus disponibles.",
  "details": [{"field": "startDate", "issue": "overlap"}],
  "timestamp": "2026-11-16T10:42:00Z"
}

Idempotence. Les endpoints de paiement acceptent une clé d'idempotence (Idempotency-Key dans l'en-tête) pour éviter les doubles déclarations en cas de nouvelle tentative réseau. Même si aucun paiement réel ne transite, la double confirmation rend ce point nécessaire.
Client généré. Le contrat OpenAPI génère les types et le client web (openapi-typescript) et les interfaces Retrofit Android (plugin Gradle OpenAPI Generator). Plan B si la génération Android pose problème : écrire à la main les 15-20 appels du niveau 1.

05Sécurité

Périmètre volontairement resserré sur quatre points à forte valeur, adaptés à un projet éducatif de trois semaines. Le reste est documenté comme perspective.

Authentification et autorisation

ÉlémentChoixJustification
AuthentificationJWT (access court + refresh)Standard, adapté au mobile
BibliothèqueSpring Security + OAuth2 Resource Server (Nimbus)Moins de code maison qu'un filtre JWT écrit à la main
Mots de passeBCrypt (coût 12)Suffisant, pas de dépendance supplémentaire
AutorisationRôles : ROLE_TENANT, ROLE_OWNER, ROLE_ADMINRBAC simple, suffisant pour trois acteurs
MFAHors périmètre niveau 1Perspective ; à mentionner au jury

Protection des API

  • Validation des entrées : Bean Validation sur tous les endpoints.
  • Rate limiting : Bucket4j sur l'authentification et la messagerie (en mémoire, une instance).
  • CORS restrictif : uniquement l'origine du frontend web.
  • Masquage des données : adresse exacte et téléphone cachés jusqu'à réservation confirmée ; filtrage des numéros écrits dans les messages.
  • OWASP Top 10 : couvert par les choix ci-dessus, sans audit formel (perspective).

Données sensibles

DonnéeMesure
CIN, justificatifs de propriétéVisibles uniquement par les admins habilités ; conservation limitée ; jamais exposés par l'API publique
Mots de passeBCrypt, jamais renvoyés par l'API
Jetons AndroidChiffrés avec une clé de l'Android Keystore (DataStore + Tink, ou EncryptedSharedPreferences si encore maintenu — à vérifier au moment du développement)
JournauxAucune donnée personnelle sensible dans les logs

Sécurité mobile

  • Stockage sécurisé des jetons (Keystore).
  • Pas de certificate pinning au niveau 1 : configuration complexe pour un bénéfice limité en démo locale.
  • Pas de détection root/jailbreak.
  • Ces deux points sont documentés comme perspectives dans le rapport.
Limite à afficher clairement. La plateforme ne détient pas l'argent et ne peut pas forcer un remboursement. Une capture d'écran est une preuve faible. La double confirmation et l'intervention de l'admin sur les cas bloqués sont les seuls leviers réels. Cette limite doit figurer dans les conditions d'utilisation et dans le rapport.
Protection des données personnelles. La loi tunisienne (INPDP) s'applique. Un avis juridique est conseillé dans un cadre réel. Pour le projet éducatif, les données de démonstration sont fausses et les documents factices.

07Organisation du code et travail multi-assistants

C'est le point qui fait la différence entre un projet cohérent et trois morceaux qui ne s'assemblent pas. Les assistants de codage accélèrent l'écriture, pas les tests ni l'intégration.

Règles de travail

  1. Un dossier docs/ servant de mémoire du projet, donné à chaque assistant en début de session : règles de la Phase 1, modèle de données, contrat OpenAPI, conventions de code, liste des décisions.
  2. Un fichier de conventions : nommage, structure des modules, format des erreurs, gestion du temps (UTC en base, Tunisie à l'affichage), montants en millimes, interdiction de renvoyer des entités JPA directement.
  3. Travail par tranche verticale : une fonction à la fois, de la base à l'écran, avec des tests, plutôt que « tout le backend » puis « tout le web ».
  4. Une branche par fonction, petites modifications, intégration continue qui bloque un code cassant les tests.
  5. Relire tout code touchant la sécurité, les paiements ou les statuts. C'est là que les assistants produisent du code qui paraît juste mais est faux.
  6. Un journal de décisions (une page par décision importante), matière directe pour le rapport.

Pièges JPA à surveiller

  • Requêtes en cascade (« N+1 ») sur la recherche : utiliser des projections DTO et des tests sur le nombre de requêtes.
  • Chargement paresseux hors transaction.
  • Entités exposées directement par l'API (fuite d'adresse exacte).

Bibliothèques optionnelles

Chaque outil est justifié, mais trois peuvent être écartés sans conséquence si le temps manque : Spring Modulith, MapStruct et la génération Kotlin. Ils sont marqués « optionnels » dans la feuille de route.

Argument pour le rapport. Le projet ne dépend d'aucun service payant et ne transmet aucune donnée personnelle à un tiers, hors Firebase au niveau 3. FCM est gratuit sans limite de messages, avec un quota de débit par défaut très large (600 000 messages/minute par projet).

Cache

Pas de Redis. Cache en mémoire avec Caffeine (via le cache de Spring) pour les données qui changent peu : villes, quartiers, configuration, saisons. Redis est présenté comme évolution en cas de plusieurs instances.

Règle de sécurité. Le cache ne doit jamais servir de données de sécurité périmées (rôles, statut de bannissement). Ne pas mettre en cache les droits ni les statuts de compte.

Performance de la recherche

  • Index sur ville, quartier, statut, type, catégorie d'usage et prix.
  • Pagination obligatoire, taille maximale limitée.
  • Une seule requête pour la liste, avec la photo principale (éviter le N+1).
  • Filtre sur les dates : exclure les annonces ayant une réservation active sur la période.
  • Test avec un jeu de données plus gros que la démo (quelques milliers d'annonces générées) pour donner un chiffre au jury.
  • Recherche texte : moteur intégré de PostgreSQL si le besoin apparaît. Pas d'Elasticsearch.

09Plan de tests

Pyramide réaliste pour trois semaines et un développeur seul.

NiveauOutilsPérimètre
Tests unitaires backend JUnit 5 + Mockito Règles métier critiques : chevauchement de dates, calcul d'acompte, transitions de statut, double confirmation de paiement
Tests d'intégration backend Testcontainers PostgreSQL Recherche et contraintes de base (anti-chevauchement)
Tests Android JUnit + MockK ViewModels
Tests E2E Aucun au niveau 1 Parcours manuel documenté pour la démo
Le test qui vaut plus que dix autres. Un test d'intégration avec deux demandes concurrentes sur les mêmes dates, qui doit renvoyer 409 BOOKING_DATES_UNAVAILABLE et non une exception non gérée. C'est là que les assistants produisent le plus souvent du code qui semble fonctionner mais échoue en concurrence.
Prérequis. Testcontainers exige Docker. Si Docker n'est pas installé ou pose problème, plan B : base PostgreSQL locale dédiée aux tests, avec la même migration Flyway. À vérifier avant la semaine 2, pas au dernier moment.
